# 通用 AI 编程协作方案：规划、实现与审查

用途：在额度有限时，由推理能力较强的 agent 负责设计与验收，另一个 agent 负责范围明确的实现工作。适用于不同项目，不绑定具体模型、平台或当前仓库任务。

本流程已整理为用户级 skill 的源码：[plan-implement-review](../skills/plan-implement-review/SKILL.md)。安装后可用 `$plan-implement-review` 调用；这是按任务启用的协作预设，不会自动启动 Gemini 或其他子 agent。若技能列表尚未刷新，可在新会话中调用，必要时重启 Codex。

统一调用模板见 [统一 Prompt](agent_collaboration_prompt.md)。复制其中的完整 Prompt，修改“本轮输入”即可。迁移到其他项目时，可复制这两份文件，也可以直接粘贴 Prompt；不要求目标项目已经存在这些文档。

## 1. 推荐的基本分工

| 角色 | 核心职责 | 交付物 |
| --- | --- | --- |
| 规划者：较强 agent | 确定问题、方案、接口、边界条件和验收标准 | 简明设计与可执行任务卡 |
| 实现者：较经济的 agent | 根据任务卡修改代码、补测试、执行检查 | 代码改动与事实性验收记录 |
| 审查者：较强 agent | 独立检查设计符合性、真实行为和测试有效性 | 按严重程度排序的问题或明确的检查结论 |
| 用户 | 提供业务目标、偏好和真实资源，决定重要取舍 | 需求与必要的约束补充 |

角色是工作方式，不要求三个不同模型同时运行。可以在不同会话中顺序完成；同一工作区尽量只有一个实现者在修改代码，审查开始前固定改动范围。

较强 agent 不必承担所有代码实现，但应保留直接编写关键小模块的选择。如果一个核心公式或兼容性处理反复解释仍出错，让它直接完成该局部实现通常比多轮返工更合适。

## 2. 按任务复杂度决定投入

| 任务 | 建议流程 |
| --- | --- |
| 文案、样式、简单配置或明确的小修复 | 实现者直接完成，按影响做检查；不必额外规划或完整审查 |
| 单模块逻辑、清晰接口下的功能 | 简短任务卡 → 实现 → 一次集中审查 |
| 跨模块状态、数值算法、数据格式、训练恢复、公共 API | 较强 agent 先定契约 → 分块实现 → 契约与集成两个检查点 |
| 新架构、目标含糊、多个方案取舍明显 | 先完成最小方案与验证设计，再交付实现任务 |

不要为每次小改动都调用完整的规划流程，也不要因为代码行数少就跳过状态、数学和兼容性判断。

## 3. 标准执行循环

### 步骤一：较强 agent 输出最小可执行设计

设计应明确以下事项，不追求篇幅：

1. 本次要改变的具体行为，以及判断成功的方法。
2. 采用的方案与关键取舍。
3. 输入输出、状态生命周期、异常行为、兼容性要求。
4. 修改范围、依赖顺序和验收标准。
5. 需要实验确认的假设，不能把假设写成已验证结论。

如果尚缺决定方案的业务信息，先推进不依赖该信息的分析，并提出最关键的问题；不要用大量未经确认的细节填补核心需求。

### 步骤二：实现者按任务卡完成一个可验收单元

一个单元应有明确行为和可检查结果，例如“新增一种配置的校验与构建”，而不是“把整个系统优化一下”。单元大小按状态与接口的复杂度控制，不按固定行数机械切割。

实现者可以自主完成局部变量、函数拆分等常规可逆选择，但不能自行改变数学定义、公共接口语义、数据协议或验收标准。

相邻且强相关的修改可以合并，例如数值预处理与有效性掩码。避免将本应一起保证的不变量拆开，制造不可用的中间版本。

### 步骤三：提交简短、可复现的交接记录

实现者提供改动范围和实际证据，而非只说“已完成”。审查者优先读取任务卡、交接记录、diff 和相关调用点，不要求重新阅读全部仓库或全部对话。

基线可以是 commit、明确 diff 或工作区快照；不是所有工具都能访问同一环境。无法读取共享仓库时，交接材料应包含必要的文件片段、差异与测试输出。不能假设审查者能看到另一会话的隐藏上下文。

默认不自动生成 commit；用户明确选择按任务提交时，可创建本地 commit 并记录 hash。无论是否提交，都不覆盖或清除用户已有改动。

### 步骤四：较强 agent 独立审查

审查重点为：

- 代码是否满足约定行为，而非只在表面上存在对应模块。
- 输入、边界、状态、兼容性和失败路径是否正确。
- 测试是否真的启用并观察了被测功能。
- 是否存在全 mock、永久走降级分支、固定零输出等导致的虚假通过。
- 真实环境、真实资产和性能验证是否有缺口。

审查默认只读，可执行合适的复现和测试。没有发现问题时说明检查范围和剩余限制，不使用“绝对正确”等保证。发现问题时给出定位、触发条件、实际影响、修复方向与回归要求。

### 步骤五：实现者处理编号明确的修复

只处理本轮问题与必要依赖，沿用原验收标准。若同类失败反复出现，应重新定位原因，并把缺少的设计决策交给规划者；不要不断扩大改动范围尝试碰运气。

修复可能影响新路径时扩大检查；无新改动、无失败、无未解疑点时，不重复跑整套相同检查。

## 4. 可复制的任务卡

```text
任务编号：T-01
目标：用一句话描述可观察的行为变化。
依据：设计文档、问题说明或用户需求；可以直接内嵌。
基线：commit / 已知 diff / 当前工作区；说明已有改动。
范围：允许修改的模块，以及必须保持的外部行为。
实现契约：输入输出、状态、异常、兼容性和关键算法。
验收标准：具体场景、预期结果、需要的证据。
依赖与未决事项：没有则写“无”。
```

不要为了填写模板制造无关字段。简单任务可以用几句话覆盖这些信息。复杂任务则应把歧义写清楚，而不是让实现者自行猜测。

验收标准由需求与设计确定。实现者可以增加覆盖，但不能为了通过而删除、跳过或降低标准；如果发现标准自身矛盾，应说明证据并请求设计决策。

## 5. 最小交接记录

```text
角色 / 任务编号：
基线 / 当前改动范围：
状态：待实现 / 已实现待审查 / 需修复 / 验收通过 / 受阻
行为与改动：最多几条，附关键文件或差异。
验收证据：标准 → 命令或复现 → 实际结果。
未运行检查与未决问题：没有则写“无”。
后续动作：下一个已定义任务，或需要回答的具体问题。
```

“已实现待审查”与“验收通过”分开记录。不能把实现者的自测通过直接标为独立审查通过。

交接记录只保留当前结果、未决问题和必要的历史引用，不需要复制长篇思考或全部终端输出。测试摘要必须来自实际执行；必要时附完整日志位置。

## 6. 验证与额度控制

- 优先做能区分正确与错误行为的检查；不为低影响的纯文档或样式改动机械编写测试。
- 有明确 bug 时，优先构造修复前会失败、修复后会通过的反例。
- 合适的 mock 用于隔离接口；至少保留与目标相称的真实集成路径。
- 功能可能被门控、缓存、回退逻辑绕过时，先证明目标路径实际发生，再检查输出。
- 将环境缺失、测试失败和验收未满足分开描述；不能用“无法运行”推导“应该通过”。
- 实现者完成环境探查、日志整理和常规执行；较强 agent 重点投入设计、歧义与独立验证。
- 按接口或集成检查点集中审查，避免每个小修改都重新规划整套系统。
- 对简单任务，短 Prompt 加现成任务卡即可；对复杂任务，再使用完整统一 Prompt。

这套分工不保证固定比例的费用节省。可以按几轮任务中的首次通过情况、返工次数和较强 agent 实际投入，决定任务卡是否还需要细化，或某个关键模块是否应由较强 agent 直接完成。

## 7. 每次如何调用

使用同一份 [统一 Prompt](agent_collaboration_prompt.md)，只切换角色和任务：

| 使用场景 | 角色 | 最少需要提供的材料 |
| --- | --- | --- |
| 有想法，需要拆解成实现任务 | 规划 | 目标、约束、现有项目或必要上下文 |
| 交给实现 agent 编码或修复 | 实现 | 任务卡；已有设计、审查编号或对应片段 |
| 检查另一个 agent 的结果 | 审查 | 任务卡、改动范围、交接记录、测试摘要 |

如果已经在同一会话建立了契约，后续可以简短调用：“角色=实现；任务=T-02；依据=既有任务卡和最新审查；完成后按统一格式交接。”不要每次复制全部历史。

不同会话之间以文档、diff 和事实性记录交接。需要用户批准的重要操作遵循当前授权与工具权限；一般实现细节不应反复请求确认。
