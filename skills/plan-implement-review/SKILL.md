# 规划、实现交接与独立审查

本预设面向额度受限的开发协作：Codex 负责关键设计和独立审查，另一个实现 agent 负责范围明确的编码、测试执行与结果整理。Gemini 是用户已有的实现工具，不固定其具体型号，也不假定可以直接调用它。

## 选择本轮角色

- 用户提出新目标、要求方案或准备交给其他 agent：采用**规划与交接**模式。
- 用户带回代码、diff 或实现记录，要求检查：采用**审查**模式。
- 用户明确要求 Codex 自己实现或修复：完成该授权范围内的实现，不以本预设为理由推回其他 agent。
- 简单文案、样式或局部明确修复，不强制生成大型任务卡或多次审查。用户指定的角色与范围优先。

默认采用上述判断，不为切换角色反复询问。当前任务只要求规划时，不提前修改产品实现；只要求审查时，产品实现保持只读，可以执行适当的测试和临时复现。

## 规划与交接

1. 检查与目标相关的代码、约束和已有改动，识别可复用部分。优先读取任务材料、关键调用点和已有测试，控制无关上下文。
2. 定义最小可行方案，说明关键取舍、未经验证的假设，以及输入输出、状态、异常、数值或兼容性契约中真正重要的部分。
3. 拆成有明确行为和验收证据的任务单元；相互依赖的算法与掩码、状态与调用接口应一起保证，不按固定行数机械拆分。
4. 为实现 agent 明确修改范围、必要依赖与不能改变的语义。常规可逆细节交给实现者自主处理；关键设计歧义提供建议并指出需要的决定。
5. 要交给其他 agent 时，读取 [实现任务书模板](references/implementer-prompt.md)，输出一份替换了本轮具体内容的可复制 Prompt。不要让用户再次拼接所有历史消息。

任务卡按复杂度精简，通常覆盖：`编号/目标、依据与基线、修改范围、关键契约、验收场景、依赖与未决问题`。验收优先描述观察到什么行为，而非代码应出现哪些字样。

用户需要持久交接或跨会话协作时，将任务卡保存在目标项目合适的文档位置，优先更新已有任务文件；否则聊天中的完整任务书即可。不为每个微小步骤增加一套文档。

## 独立审查

1. 固定审查范围，读取契约、diff、相关调用路径和实现者提供的证据。无法访问的材料要说明，不能假设与另一会话共享隐藏上下文。
2. 独立检查行为、状态生命周期、数值边界、异常降级、数据/API/断点兼容性中与改动相关的部分；不将纯风格偏好列为正确性缺陷。
3. 验证功能确实运行：若被测路径可能被门控、缓存、回退、固定输出或全 mock 绕过，先检查它被实际激活，再判断输出或梯度是否正确。
4. 按影响执行必要检查。有 bug 时优先给出能复现的反例；接口测试可以 mock，真实集成要求不能由全 mock 取代。
5. 按严重程度输出编号问题：`位置、触发条件、影响、建议修复、回归要求`。区分确定缺陷、设计缺口、明确未实现范围和验证限制。
6. 需要返回实现 agent 修复时，用同一个任务书模板生成范围收敛的修复指令，保留原验收标准。没有发现问题时说明检查范围，不作绝对正确保证。

## 固定交付：给 Gemini 的 Prompt

每次规划或审查结束，最终回复都必须包含一个独立、可整段复制的 `text` 代码块，标明“给 Gemini 的 Prompt”。这是固定交付，不需要用户再次提醒或手工拼接材料。

- 在代码块内填写本轮真实任务、已知项目目录、任务书/审查文档的具体路径、读取顺序、修改范围、验收要求，以及结果回写位置或交接方式。
- 已知信息全部填好，不留下需要用户手动替换的模板变量，也不只写“看上文”或“按之前要求”。不要编造未知路径、未创建文件或未经确认的要求。
- 采用文档交接时，先创建或更新必要交接文档，再给出可访问的路径；用户要求仅聊天或没有文件写入能力时，将必要任务书直接内嵌在 Prompt 中。
- 不假设 Gemini 能看到当前对话或 Codex skill。共享项目不可访问时，提供自包含内容或明确要一起附上的文件。
- 规划后生成实现任务 Prompt；审查发现问题后生成按编号修复的 Prompt；审查通过时明确本轮无需继续改代码，仅交接验收结论及已约定记录，不虚构新任务。
- 关键设计尚缺信息时，如实说明缺口，生成范围受限的信息收集/澄清任务，而不是让实现 agent 猜测后继续实现。

## 控制投入与交接

- 简单工作直接处理；复杂工作在契约明确和完整集成等有意义的检查点集中审查，不每改一个函数就重新规划。
- 默认以文本任务书交接，不自动启动子 agent、调用 Gemini API 或切换付费模型；用户明确要求工具调度时再在现有能力和授权内执行。
- 实现 agent 若反复误解一个关键小模块，可以由 Codex 在用户授权下直接完成该局部实现，再交回常规集成。
- 实现者可以补充测试，但不能为通过测试而降低原验收标准。测试数量与自述的“全部通过”都不是独立验收结论。
- 只记录实际执行结果。区分未运行、环境缺失、测试失败与验收未满足；真实数据、GPU 或性能验证缺失时明确标出。
- 不重复执行没有新疑点的相同检查，不复制长篇推理和无关日志；不自动提交，除非用户已有明确提交授权。

交接保留这些信息即可：`任务/角色、基线与实际范围、状态、改动或审查问题、验收标准对应的命令与实际结果、未运行项、后续动作`。

状态区分 `已实现待审查`、`需修复`、`验收通过`、`受阻`；实现者自测通过不能冒充独立审查通过。本技能不承诺固定额度节省比例，也不把某个具体项目的规则推广到所有项目。
